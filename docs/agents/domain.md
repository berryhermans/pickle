# Domain documentation

Use a single-context layout for domain terms and architectural decisions:

- Read the root `GLOSSARY.md` when working with domain terminology.
- Read relevant decisions in `docs/adr/` before proposing or changing architecture.
- If either location is absent, continue without treating that as a setup problem; create documentation when a decision or domain term warrants it.

Use glossary terminology consistently. If a needed term is not defined, identify it as a candidate to resolve rather than silently inventing a competing term. Call out conflicts between a proposed change and a relevant ADR.
